# 职业发展规划

> [!summary] 当前方向
> 以 **Java 后端＋能源／IoT 业务** 为主线，先用 6～12 个月补齐独立开发、验证和排障能力，再结合面试反馈决定跳槽时机。两年是最晚期限，不是必须等待的时间。
> 本文记录个人情况与当前建议；具体执行见 [[技术学习计划]]。建议尚需结合项目实践和招聘反馈调整，不代表已经完成能力验证。

## 2. 能力现状与主要问题

### 可以继续积累的经验

- 已经接触真实设备、厂家、现场上线和生产部署。
- 有协议开发和 IoT 层改造经历，可以进一步沉淀为系统设计、通信与排障案例。
- 现有技术栈能够支撑通用 Java 后端能力的学习。

### 当前需要补齐的能力

- 新协议开发主要由 AI 根据文档生成解析等代码，部分代码自己尚不能充分理解。
- Java 并发、网络、Linux、数据库等基础自评不牢固，面试准备不足。
- 部署操作较熟练，但解决问题仍较依赖 AI，需要补齐解释原因、独立验证的能力。
- 尚未从零实践完整的权限模块，完整业务模块交付经验不足。
- 工作内容零散，容易积累任务数量，却难以形成能深入讲清的项目成果。

> [!important] 当前最优先的改变
> 把已经交付的工作转化成自己的能力：负责的关键代码必须能解释、能验证、能修改。继续使用 AI，但由自己判断设计与实现是否正确。

设备台数本身不能证明高并发挑战。先关注消息正确性、异常恢复、接入效率和定位问题的能力；性能优化由消息频率、峰值、延迟等实测证据驱动。

## 3. 职业定位与下一份工作

### 主线

目标为杭州 Java 后端岗位，优先考虑能源、设备平台、工业物联网等能够延续现有经历的业务，同时对其他业务后端保持开放。

- 通用后端能力是基础：业务建模、数据库、接口、消息处理、测试、部署与排障。
- 能源／IoT 经验是可积累的业务优势：协议接入、设备状态、指令与上报、异常处理。
- AI 作为开发与学习工具融入日常；暂不单独投入大模型训练、算法转岗或 AI 应用转岗路线。

### 下一家公司需要重点考察

- 能否负责需求、设计、开发、测试、上线的完整模块。
- 是否有代码审查，以及可以讨论设计和故障的资深工程师。
- 开发、厂家对接、客户支持的实际比例。
- 是否能积累数据库、消息可靠性、业务建模等可迁移经验。
- 薪资、工作强度、成长空间是否综合改善。

薪资目标暂不定数。比较机会时统一看税前年薪、奖金、公积金基数及工作强度，不直接把税后月收入与招聘月薪比较。

## 4. 阶段路线

以实际开始执行时间为起点；下列为建议安排，各阶段均未验收。

| 阶段 | 重点 | 验收成果 |
|---|---|---|
| 第 1～2 个月 | 掌握现有 IoT 链路，补相关 Java 和网络基础 | 一份消息链路说明、一组可运行的报文测试，能独立解释和复现几类异常 |
| 第 3～4 个月 | 深入一个真实可靠性问题 | 一份包含现状证据、原因、方案、验证结果的改进案例 |
| 第 5～6 个月 | 补齐完整业务模块开发 | 需求说明、表与接口设计、权限边界、测试和上线记录形成闭环 |
| 第 7～12 个月 | 项目复盘、面试基础、少量投递 | 两个能深入讲清的项目案例，根据面试反馈更新能力缺口与跳槽安排 |
| 第 13～24 个月（如仍未跳槽） | 根据机会与反馈调整 | 每季度复盘岗位匹配和主要短板，避免只延长学习清单；最晚期限前推进实际求职 |

第 6 个月安排一次能力复盘，达到基本标准即可开始少量投递。后半程不预排过细，按实际进展调整。

## 5. 怎样把现有工作做深

### 掌握一条协议链路

选一个熟悉的协议，追踪心跳或充电状态上报：入口 Handler → 消息边界 → 字段解析与校验 → 设备和连接关联 → 业务处理 → 消息／缓存／持久化。以真实代码为准，不假定每条消息都经过全部中间件。

逐步回答：半包如何处理、重连后旧连接如何处理、重复消息有什么后果、下游失败会怎样、日志能否确定失败位置。

### 选一个真实问题改进

候选包括：厂家报文差异难排查、掉线状态更新不及时、数据推送失败缺少补偿、重复消息导致重复处理、新协议依赖现场试验而缺少回放验证。

先确认问题真实存在并记录现状，再选择范围有限的改进。没有测量数据，不编造提升比例；不为学习而直接改造生产系统。

### 争取一个完整业务模块

优先选择能源平台真实需要的小模块，如设备告警记录、第三方推送任务管理或设备接入配置。自己完成需求确认、表与接口设计、实现、权限、测试、上线和效果观察。

医疗监管平台作为备选，先确认职责、业务价值和可控范围，再决定投入。

## 6. AI 使用与同事协作

每次任务先自己整理输入输出、协议规则、异常条件与处理流程，再让 AI 分段实现。

- 关键代码能够解释输入、输出、失败条件及设计假设。
- 能使用适用的正常、截断、错误长度、错误校验、重复消息等样例验证行为。
- 不依赖 AI 的现成解释，也能画出流程、定位修改位置。
- 遇到陌生 API 或框架行为，结合当前项目版本查阅官方文档和实际验证。

建议尝试每两周请资深同事审查一个具体成果，例如流程图、关键代码或设计方案。先给出自己的判断，再请对方指出漏洞；尚未约定固定审查安排。
