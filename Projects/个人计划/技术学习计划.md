# 技术学习计划

> [!summary] 主线与目标
> 围绕当前能源／IoT 工作补齐 Java 后端能力，把现有协议开发、部署和改造经历转化为可以独立解释、验证、修改的能力。
> 背景、择业标准与长期安排见 [[职业发展规划]]。本页记录执行计划；任务尚未开始验收。

## 1. 计划原则

1. 每次聚焦一个项目问题，补齐相关基础，以成果验收。
2. 同时最多推进两个重点，当前为后端与 IoT、相关网络与排障基础。
3. AI 继续辅助开发；关键代码由自己理解、验证并负责。
4. 按每周 5～7 小时保守安排，不把所有可能出现的碎片时间都计入。
5. 状态只使用：未开始／进行中／暂停／已完成。写入计划不等于已经开始执行。

## 2. 现状盘点

| 领域 | 当前情况（本人自述） | 下一阶段目标 |
|---|---|---|
| Java 后端 | 使用 Spring Boot、MySQL、Redis、Kafka，任务较零散，基础不牢固 | 理解现有代码，逐步独立完成业务模块 |
| IoT 与 Netty | 独立承担协议开发，IoT 层改过一版；较依赖 AI，部分生成代码看不懂 | 掌握真实消息链路，验证异常与可靠性 |
| 部署与 Linux | 部署实践较多，解决问题较依赖 AI | 能依据日志、进程、端口等证据定位常见故障 |
| 数据库与并发 | 自评基础不足 | 结合实际场景理解事务、索引、线程安全 |
| 认证与权限 | 未从零实践完整模块 | 在小型业务模块中实践认证、授权与数据边界 |
| AI 工具 | 经常使用 AI 写解析、辅助部署 | 能判断生成结果并设计验证方法 |

旧版依据本机软件推测的能力不作为已确认事实；研究方向与英语水平仍待补充。

## 4. 从项目问题补基础

| 实际问题 | 对应知识 | 验证方式 |
|---|---|---|
| 消息分段到达、连续报文 | TCP 字节流、缓冲区、Netty 编解码 | 将一条报文拆分输入、将多条报文连续输入，检查解码结果 |
| 并行更新设备状态 | Java 并发、共享状态、线程安全 | 梳理实际执行线程，构造并行更新场景 |
| 消费失败、重复消息 | Kafka 消费确认、重试、幂等 | 在测试环境模拟处理失败和重复消费，检查业务结果 |
| 数据状态不一致、慢查询 | MySQL 事务、索引、执行计划 | 复现失败路径，查看实际 SQL 与执行计划 |
| 缓存与连接状态异常 | Redis 数据结构、过期、状态同步 | 检查缓存生命周期，验证重连和过期行为 |
| 服务启动或连接失败 | Linux 进程、端口、日志、资源 | 记录证据、定位原因、验证修复 |

不要求同时完成全部条目，按当前协议链路出现的问题排序。

## 5. 阶段里程碑

| 周期 | 目标 | 验收标准 | 状态 |
|---|---|---|---|

| 第 7～12 个月 | 项目表达与面试准备 | 能深入讲清两个案例，记录并处理面试反馈 | 未开始 |

## 6. 首两周任务：掌握一个现有协议

选定协议：〔待选〕；典型消息：〔心跳或充电状态上报，待选〕。

### 第一周：读懂与梳理

- [ ] 选一个熟悉且有可用样例的协议，收集协议文档与脱敏报文。
- [ ] 找到入口 Handler、消息边界判断、解析与校验、业务处理的位置。
- [ ] 画出从设备到实际下游存储的链路，标注相关线程和组件。
- [ ] 列出最多 5 个当前看不懂的问题，先解决影响主链路理解的问题。
- [ ] 不依赖 AI 的现成说明，用自己的话讲一遍消息处理过程。

### 第二周：验证与审查

- [ ] 写正常报文测试，核对关键字段。
- [ ] 根据协议适用性，加入分段输入、连续报文、错误长度、错误校验等测试。
- [ ] 选一种异常，记录实际行为、预期行为和原因；额外关注重复消息或重连行为。
- [ ] 请资深同事审查一次流程图或关键实现，记录反馈；时间需与对方协调。
- [ ] 整理一页总结：已经理解什么、发现什么、还缺什么。

验收产出：一张链路图、一组可运行测试、一份问题与结论记录。图和笔记放在合适的项目笔记中，代码与测试保存在获准使用的项目开发环境中。

## 7. 每周执行节奏

| 时间安排 | 内容 |
|---|---|
| 3 次，每次 30～45 分钟 | 阅读项目代码，补一个相关基础点 |
| 1 次，约 90 分钟 | 连续完成测试、异常复现或小实验 |
| 1 次，约 60 分钟 | 整理成果、问题与下周重点 |
| 其余可用时间 | 处理未完成验证，后期逐步加入 Java、SQL、算法面试练习 |

忙碌周最低目标：弄懂一条小链路，做一个验证。没有完成时缩小范围，不叠加下一周任务。

## 8. AI 辅助开发检查

- [ ] 先自行写清输入、输出、流程、协议假设与异常条件。
- [ ] 让 AI 分段实现，关键代码逐段理解。
- [ ] 使用独立于生成实现的预期结果验证行为，避免只证明代码能运行。
- [ ] 能说明失败会发生什么、日志如何定位、应该改哪里。
- [ ] 涉及框架行为时核对项目实际版本和官方文档。

## 9. 复盘机制

每周用约 15 分钟记录：实际产出、主要卡点、下周唯一重点。每月检查是否能独立解释与修改更多代码；每季度检查职业方向与岗位需求是否仍匹配。

| 周期 | 实际产出 | 卡点 | 下一步 |
|---|---|---|---|
| 首两周 | 〔完成后填写〕 | 〔待填〕 | 掌握一个现有协议 |
